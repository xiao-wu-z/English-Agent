# AI 英语口语陪练助手 - 基准设计文档

## 目标

开发一个两天内可交付的 MVP：多场景 AI 英语口语陪练助手。

用户可以选择一个练习场景，用语音和 AI 进行实时英语对话。AI 根据场景扮演对应角色，使用语音回复用户，并在对话过程中给出轻量纠错。练习结束后，系统生成一份结构化总结，帮助用户了解本次表现、主要错误和下一步提升方向。

第一版不做登录、不做数据库、不做后台管理，练习历史保存在浏览器本地。

## 背景和设计取舍

题目要求的是一个真实英语口语练习工具，不是普通文本聊天机器人。核心体验是“用户说英语，AI 立刻用语音回应”，所以第一版应该优先保证语音链路流畅、场景自然、反馈有用。

两天开发时间不适合直接做工业级完整平台。更合理的路线是：

- 先做可用的多场景语音陪练 MVP。
- 场景用 JSON 配置文件管理，给后续扩展留结构。
- 历史记录先放在浏览器本地，避免登录和数据库带来的复杂度。
- 发音反馈先做“可理解度、清晰度、常见问题”层面，不承诺专业音素级评分。

这样第一版能覆盖题目要求，同时不会把时间耗在后台、账号体系、数据库和管理界面上。

## 第一版范围

### 包含

- 多场景选择。
- 至少五个内置场景：
  - 面试英语
  - 餐厅点餐
  - 商务会议
  - 机场或旅行
  - 日常闲聊
- 场景配置文件。
- 场景配置校验。
- 实时语音输入。
- 实时语音输出。
- AI 根据场景进行角色扮演。
- 对话中的轻量纠错。
- 练习后的结构化总结。
- 本地历史记录。
- TypeScript + Next.js 技术栈。

### 不包含

- 用户登录。
- 服务端数据库。
- 后台场景管理。
- 移动端原生 App。
- 专业音素级发音评分。
- 课程体系、排行榜、社交功能。

## 用户体验

### 进入页面

用户进入应用后，首先看到场景选择区和最近练习记录。

场景卡片需要展示：

- 场景名称
- 难度
- 场景说明
- 用户练习目标
- AI 扮演角色

用户选择一个场景后，进入练习房间。

### 练习房间

练习房间是第一版的核心页面。它需要清晰展示：

- 当前场景
- AI 角色
- 练习目标
- 连接状态
- 开始和结束按钮
- 对话字幕
- 纠错建议

用户点击开始后，浏览器请求麦克风权限，然后建立实时语音连接。用户说话后，AI 用语音自然回应。

### 对话方式

AI 不应该像一个机械问答机器人，而应该像真实场景中的对话对象。

例如：

- 面试场景中，AI 是面试官。
- 餐厅场景中，AI 是服务员。
- 商务会议中，AI 是同事或主持人。
- 旅行场景中，AI 是机场工作人员或酒店前台。
- 日常闲聊中，AI 是普通英语对话伙伴。

AI 应该一次只推进一个问题或话题，并根据用户回答继续追问。

### 纠错方式

对话中的纠错要克制，不能频繁打断用户。

实时纠错只展示轻量建议，例如：

- 语法错误
- 更自然的表达
- 发音或清晰度提醒
- 推荐替代表达

更详细的分析放到练习结束后的总结里。

### 课后总结

用户结束练习后，系统生成一份总结报告。

总结报告包含：

- 总体评分
- 流利度评分
- 发音清晰度评分
- 语法准确度评分
- 表达自然度评分
- 本次优点
- 主要问题
- 错误句子和修改建议
- 推荐表达
- 下次练习建议

总结生成后保存到本地历史记录。

## 技术架构

### 技术栈

- Next.js App Router
- TypeScript
- Tailwind CSS
- Zod
- OpenAI Realtime API
- WebRTC
- 浏览器 `localStorage`

### 为什么使用 WebRTC Realtime

这个产品的核心是实时口语陪练。相比“录音上传 -> 语音转文字 -> 大模型生成 -> 文字转语音”的串联方式，Realtime + WebRTC 更适合低延迟语音对话。

串联方式可以做，但延迟更高，用户会明显感觉不像真实对话。第一版应该优先选择实时语音链路。

### 整体流程

1. 用户打开应用。
2. 前端加载场景配置。
3. Zod 校验场景配置是否正确。
4. 用户选择一个场景。
5. 用户点击开始练习。
6. 浏览器请求麦克风权限。
7. 前端请求 Next.js API 创建实时会话。
8. 服务端使用 OpenAI API Key 创建会话。
9. 浏览器通过 WebRTC 建立语音连接。
10. 用户语音发送给 AI。
11. AI 语音返回给用户。
12. 实时事件更新字幕、连接状态和纠错建议。
13. 用户结束练习。
14. 系统根据对话内容生成总结。
15. 总结展示在页面上，并保存到 `localStorage`。

## 场景配置设计

第一版使用 JSON 文件定义场景。这样既能满足“多场景可配置”，又不需要做后台管理。

建议目录：

```txt
src/scenarios/job-interview.json
src/scenarios/restaurant.json
src/scenarios/business-meeting.json
src/scenarios/travel.json
src/scenarios/small-talk.json
```

每个场景至少包含：

- 场景 ID
- 场景标题
- 场景说明
- 难度
- AI 角色
- 用户角色
- 开场白
- 练习目标
- 实时对话指令
- 纠错策略
- 总结评分标准

示例：

## 主要模块

### 场景模块

负责加载、校验和暴露场景配置。

它的目标是让新增场景尽量简单。后续如果要增加“客户谈判”“留学面试”“学术会议”等场景，只需要增加配置文件，不需要大改业务代码。

### 语音会话模块

负责管理实时语音连接。

它需要处理：

- 麦克风权限
- WebRTC 连接
- AI 音频播放
- 会话开始
- 会话结束
- 连接错误
- 重连入口

### 对话记录模块

负责展示用户和 AI 的对话字幕。

字幕不是第一版最难的部分，但它对总结、纠错和用户复盘很重要。

### 纠错模块

负责展示对话中的轻量反馈。

第一版可以优先展示：

- 原句
- 修改建议
- 简短原因
- 类型标签

### 总结模块

负责生成和展示课后总结。

总结需要是结构化数据，不能只是普通长文本。结构化数据更适合做 UI 展示，也方便保存历史记录和后续做统计。

### 历史记录模块

负责把总结保存到 `localStorage`。

第一版建议最多保存最近 20 条。这样用户刷新页面后仍然能看到最近练习结果，但不会引入登录和数据库复杂度。

## API 设计

### 创建实时语音会话

`POST /api/realtime/session`

输入：

- `scenarioId`

职责：

- 找到对应场景配置。
- 校验配置。
- 组装该场景的实时对话指令。
- 使用服务端 OpenAI API Key 创建实时会话。
- 返回前端建立连接所需的信息。

### 生成练习总结

`POST /api/session/summary`

输入：

- `scenarioId`
- `transcript`
- `durationSeconds`

职责：

- 找到对应场景配置。
- 使用场景评分标准生成总结。
- 返回结构化 JSON。

## 数据结构

### 对话记录

```ts
type TranscriptItem = {
  id: string;
  role: "user" | "assistant";
  text: string;
  createdAt: string;
};
```

### 纠错建议

```ts
type CorrectionItem = {
  id: string;
  type: "grammar" | "pronunciation" | "expression" | "vocabulary";
  original?: string;
  suggestion: string;
  explanation: string;
  createdAt: string;
};
```

### 练习总结

```ts
type PracticeSummary = {
  id: string;
  scenarioId: string;
  scenarioTitle: string;
  createdAt: string;
  durationSeconds: number;
  scores: {
    overall: number;
    fluency: number;
    pronunciation: number;
    grammar: number;
    expression: number;
  };
  strengths: string[];
  issues: string[];
  correctedSentences: Array<{
    original: string;
    corrected: string;
    reason: string;
  }>;
  recommendedExpressions: string[];
  nextPracticeSuggestions: string[];
};
```

## 错误处理

第一版至少要处理这些情况：

- 用户拒绝麦克风权限。
- 实时连接失败。
- OpenAI API Key 未配置。
- 场景配置格式错误。
- 总结生成失败。
- 本地历史记录保存失败。

错误提示要清晰，尤其是麦克风权限和连接失败，必须给用户重新尝试的入口。

## 验收标准

第一版完成时，需要满足：

- 使用 Next.js + TypeScript 实现。
- 至少有五个场景。
- 场景来自 JSON 配置。
- 场景配置有 schema 校验。
- 用户可以进行语音输入。
- AI 可以进行语音输出。
- AI 能按照场景角色进行对话。
- 用户可以结束练习。
- 系统可以生成结构化总结。
- 总结包含评分和改进建议。
- 总结可以保存到本地历史记录。
- 前端代码不暴露正式 OpenAI API Key。

## 当前决策

- 第一版做多场景，而不是单一面试场景。
- 第一版做 JSON 配置场景库，而不是后台管理。
- 第一版做本地历史记录，而不是登录和数据库。
- 第一版优先实时语音体验，而不是复杂课程系统。
- 第一版保留扩展点，但不提前实现工业级平台能力。
