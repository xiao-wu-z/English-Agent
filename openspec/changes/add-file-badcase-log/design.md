## Context

English-Agent 后续接真实模型后，最容易出现的问题不是“完全不能运行”，而是评测过度自信、纠错误导、总结空泛、provider 输出不符合 schema。这些问题需要证据闭环。`ai-tuoke-mt-agent` 使用 badcase signal、judge 和状态流转做持续优化，但它依赖更重的存储和评审体系。English-Agent V1 没有向量库、数据库或后台管理，因此先做 file-based badcase log。

Badcase 在三层 Prompt 架构中的角色是 Tier 3：它是动态、按 scenario/skill/task 相关性筛选的运行态提示，不是全局红线，也不是 Skill 本身。

## Goals / Non-Goals

**Goals:**

- 定义 `BadcaseSignal` 数据合同。
- 用 JSONL 文件记录 badcase signal。
- 按 kind 映射到 correction、assessment、summary、provider 四类文件。
- 提供 append/read helper。
- 支持自定义存储根目录，测试不污染真实 `data/`。
- 定义 `BadcaseHint` 数据合同。
- 提供 `toBadcaseHint` 和 `getRelevantBadcaseHints`。
- 明确 BadcaseHint 是未来 Prompt Runtime 的 Tier 3 输入。

**Non-Goals:**

- 不实现自动 judge。
- 不实现向量检索。
- 不实现 SQLite、Redis、MySQL 或 Milvus。
- 不实现后台管理 UI。
- 不实现 badcase review 工作台。
- 不实现 regression runner。
- 不改 Agent Skill Runtime。

## Decisions

### Decision 1: 使用 JSONL 而不是 JSON 数组

JSONL 适合 append-only 日志，每次写入一行，不需要读全文件再写回。它也方便后续转成回归样本或迁移到 SQLite。

替代方案是单个 JSON 数组文件。它在 append 时需要读写整个文件，容易被并发写破坏，也不适合持续增长。

### Decision 2: 按 kind 映射文件

文件映射：

```text
correction.jsonl:
  wrong_correction
  user_dismissed_correction

assessment.jsonl:
  low_quality_assessment

summary.jsonl:
  bad_summary
  user_regenerated

provider.jsonl:
  provider_schema_failure
```

这样后续人工复盘和测试可以按类别读，不需要每次扫全部日志。

### Decision 3: BadcaseSignal 存证据，BadcaseHint 进 prompt

`BadcaseSignal` 可以包含完整 input snapshot，例如 user text、assistant text、correction、assessment、summary 或 provider raw text。它用于复盘和回归。

`BadcaseHint` 是 prompt-safe 的短提示，只包含：

```ts
{
  kind;
  scenarioId;
  skillId;
  lesson;
  avoidPattern;
  suggestedBehavior;
  sourceSignalId;
}
```

未来 T3 只注入 `BadcaseHint[]`，不注入完整 input snapshot，避免 prompt 过长和泄露过多上下文。

### Decision 4: 相关性先用文件过滤，不做向量检索

V1 没有向量库。`getRelevantBadcaseHints` 先按 `scenarioId`、`skillId`、kind 和 limit 过滤最近记录。后续可以升级为 SQLite 或向量检索，但接口先稳定。

### Decision 5: 测试必须传临时 root

真实默认目录是 `data/badcases`，但测试必须使用临时目录，例如 `/private/tmp/english-agent-badcases-*`。这样测试不会污染演示数据。

## Data Flow

```text
user feedback / provider validation / system check
        ↓
BadcaseSignal
        ↓
appendBadcaseSignal
        ↓
data/badcases/<category>.jsonl
        ↓
readBadcaseSignals
        ↓
getRelevantBadcaseHints
        ↓
BadcaseHint[]
        ↓
future Prompt Runtime Tier 3
```

## Error Handling

- Invalid signal schema: reject before writing.
- Unknown kind: reject via schema.
- Invalid JSONL line: throw parse error with file path and line number.
- Missing file: read returns empty list.
- Directory missing: append creates directory.
- Empty lines: read skips them.

## Prompt Placement

Badcase hints belong to Tier 3:

```text
Tier 1: Core Coach Rules
Tier 2: Scenario + Active Skill
Tier 3: Runtime State + Relevant Badcase Hints
```

Specific badcases should not be written into Tier 1 because they are not global rules. They should not be written into Tier 2 because they are not part of scenario or Skill identity. They are runtime context selected for the current session/task.

## Risks / Trade-offs

- [Risk] JSONL grows without bound → Mitigation: V1 keeps logs small; later add rotation or SQLite migration.
- [Risk] File append race in high concurrency → Mitigation: V1 Demo traffic is low; later introduce queue or database if needed.
- [Risk] Badcase hints overfit to old mistakes → Mitigation: hints are filtered by scenario/skill and limited; status can be reviewed/ignored.
- [Risk] Sensitive transcript content stored on disk → Mitigation: V1 local demo only; do not inject full inputSnapshot into prompt, only short hints.

## Migration Plan

No migration is required.

Implementation order:

1. Define schemas.
2. Implement file path mapping.
3. Implement append/read helpers.
4. Implement hint conversion and relevant hint lookup.
5. Add tests with temporary directories.
